# RAG: поиск и генерация

## Что такое RAG в нашем проекте

RAG = Retrieval-Augmented Generation.
Сначала находим релевантные документы, потом передаём их в LLM,
чтобы модель отвечала на основе реальных данных, а не «из головы».

В нашем случае:

1. Корпус — описания клиентов из Credit Card Customers.
2. Поиск — BM25 по этим описаниям.
3. Генерация — LLM формирует ответ с рекомендацией.

## Корпус

### Источник

Credit Card Customers (Kaggle).
Файл `data/BankChurners.csv`.

### Преобразование в текст

Каждая строка CSV → одно описание клиента.

Поля, которые попадают в текст:

- `Customer_Age` — возраст;
- `Gender` — пол;
- `Income_Category` — доход;
- `Card_Category` — тип карты;
- `Months_on_book` — сколько месяцев клиент с банком;
- `Total_Trans_Amt` — сумма транзакций;
- `Total_Trans_Ct` — число транзакций;
- `Contacts_Count_12_mon` — обращения в поддержку;
- `Attrition_Flag` — ушёл / остался.

Пример описания:

```
Клиент 45 лет, жен. Доход $60K–$80K. Карта Platinum.
С банком 36 месяцев. Транзакций за год: 120.
Сумма транзакций: $4500. Обращений в поддержку: 3.
Статус: ушёл.
```

Описания генерируются на русском языке скриптом `corpus.js`.
Это позволяет использовать русские стоп-слова при поиске.

### Размер корпуса

На КТ1 — подвыборка 1000–5000 клиентов,
чтобы уложиться в браузер.

На КТ2 — полный датасет или backend.

## Поиск: BM25

### Параметры

- `k1 = 1.5`
- `b = 0.75`

Это стандартные значения. Если benchmark покажет плохие
результаты, можно подобрать заново.

### Предобработка

1. Приведение к нижнему регистру.
2. Удаление знаков препинания.
3. Токенизация по пробелам.
4. Стоп-слова — минимальный список (и, в, на, с, по).
   Список русский, потому что корпус описаний — на русском.

### Реализация

Варианты:

- библиотека `bm25-turbo` (WASM, работает в браузере);
- библиотека `fast-bm25` (TypeScript) — запасной вариант;
- собственная реализация — около 80 строк.

На КТ1 поиск — заглушка внутри `index.html`.
Реальный `bm25.js` появится после КТ1.
Выбор библиотеки на КТ1 можно не фиксировать.

Интерфейс `bm25.js`:

```js
export function buildIndex(docs) { ... }
export function search(query, k) { ... }
```

### Вход и выход

- Вход: строка запроса, число `k`.
- Выход: массив `{ doc, score }`, отсортированный по убыванию.

## Генерация: LLM

### Промпт

Шаблон промпта:

```
Ты — помощник менеджера по удержанию клиентов.
Ответь на вопрос пользователя, опираясь только на факты
из приведённых документов. Если данных недостаточно,
скажи об этом прямо.

Вопрос:
{query}

Документы:
{documents}

Ответ:
```

### Провайдеры

- `mock` — заглушка для КТ1, возвращает шаблонный текст.
- OpenAI API — простой вызов, нужен ключ.
- WebLLM — модель работает в браузере на WebGPU,
  ключ не нужен, но требует совместимого устройства.

На КТ1 используется `mock`. Переключение — через `config.js`.

### Ограничения

- Контекст модели ограничен — передаём не больше 5 документов.
- Если ответ не опирается на документы — помечаем как ненадёжный.
- Таймаут вызова — 30 секунд.

## Benchmark

### Набор

Файл `benchmark/questions.json`:

```json
[
  {
    "query": "Клиент 45 лет, карта Platinum, транзакции упали",
    "relevant_ids": ["C12345", "C67890"]
  }
]
```

### Метрики

- **Recall@5** — доля релевантных клиентов в топ-5.
- **Precision@5** — доля релевантных среди топ-5.
- **MRR** — средний обратный ранг первого релевантного.

### Запуск

```
node benchmark/run.js
```

Результат сохраняется в `benchmark/results.json`.

## Что проверяется на КТ1

- Корпус описан и понятен.
- Интерфейс поиска определён (`search(query, k)`).
- Промпт и провайдер LLM выбраны.
- Benchmark спланирован.

Работающий поиск и вызов LLM на КТ1 не требуются.
